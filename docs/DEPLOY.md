# Рабочая схема Quiby

- `https://mess.quiby.me/` — сайт загрузки.
- `https://mess.quiby.me/app` — веб-клиент и адрес настольного приложения.
- `https://mess.quiby.me/messenger/*` — REST API, файлы, SSE, версия и список сборок.

Cloudflare Tunnel `quiby-core` связан с Docker-сетью `quiby-core_default`. Galinka подключается к этой сети через `compose.edge.yml`. Единственный необходимый маршрут:

| Hostname      | Path  | Service               |
| ------------- | ----- | --------------------- |
| mess.quiby.me | любой | `http://galinka:3001` |

Домен `api.quiby.me` обслуживает отдельный проект Quiby через VPS. Galinka его не использует. REST API, файлы и SSE доступны через `/messenger` на собственном домене; приложение преобразует этот префикс во внутренний `/api`. VPS и маршрут API Quiby менять не нужно.

В `.env` на сервере:

```dotenv
APP_ORIGIN=https://mess.quiby.me
PUBLIC_API_ORIGIN=https://mess.quiby.me
VITE_API_BASE=/messenger
COOKIE_SECURE=true
TRUST_PROXY=1
EDGE_NETWORK=quiby-core_default
BUILD_SHA=0.3.1
```

Запуск: `docker compose -f compose.yml -f compose.edge.yml up -d --build`. Для каждого деплоя задавайте `BUILD_SHA` актуальным коммитом или версией; это же значение попадает в клиент, service worker и API версии. Локальный доступ к cookie по HTTP при `COOKIE_SECURE=true` не работает — используйте публичные HTTPS-домены.

В настройках приложения «Проверить обновления» сравнивает версию интерфейса с сервером. Настольная оболочка проверяет GitHub Releases и скачивает обновление только по нажатию пользователя. macOS auto-update требует подписанной сборки.

# Управляемая установка Galinka

Рабочий экземпляр находится в `/DATA/AppData/Galinka`. Файл `.env` — `/DATA/AppData/Galinka/.env`; действующая конфигурация карточки CasaOS — `/var/lib/casaos/apps/galinka-app-1/docker-compose.yml`. Она содержит секреты и не должна попадать в репозиторий.

Приложение `galinka-app-1` использует отдельный образ `galinka-app:0.4.1`. Для включения, выключения и перезапуска используйте карточку Galinka в CasaOS. Постоянные тома — `galinka_postgres` и `galinka_uploads`; при обновлении заменяется только контейнер приложения.

Перед выпуском 0.4.1 сохранены база, файлы и предыдущая конфигурация в `/DATA/AppData/Galinka/.deploy/0.4.0`. Каталог `.deploy` исключён из Git и контекста Docker.

Обновления клиента проверяются при запуске, возвращении в приложение и раз в 10 минут. Кнопка загрузки в сайдбаре видна при доступной новой версии. Windows и AppImage загружают и устанавливают обновление из приложения; Android требует системного подтверждения установки APK. Arch Linux обновляется новым пакетом. Неподписанный macOS — новым DMG. На iPhone устанавливается веб-приложение через Safari; его интерфейс обновляется с сайта.

# Galinka на CasaOS

## 1. Подготовить каталог и секреты

На машине CasaOS в терминале (локально или через SSH):

```sh
mkdir -p /DATA/AppData
cd /DATA/AppData
git clone https://github.com/cl0rex1/Galinka.git
cd Galinka
docker run --rm --user "$(id -u):$(id -g)" -v "$PWD:/workspace" -w /workspace node:24-alpine node scripts/setup.mjs
```

Скрипт создаёт `.env` с правами `0600`, случайными паролем PostgreSQL и кодом регистрации. Повторный запуск не меняет существующий файл. Он не печатает секреты в консоль. Если `git` отсутствует, распакуйте архив исходников в этот каталог.

Откройте `.env` редактором и задайте:

```dotenv
APP_ORIGIN=https://chat.example.com
COOKIE_SECURE=true
TRUST_PROXY=1
```

`APP_ORIGIN` — ваш настоящий домен **без завершающего слеша и пути**. `TRUST_PROXY=1` подходит, если перед Node.js ровно один reverse proxy. Закройте прямой внешний доступ к порту 3010, оставив его доступным прокси. Если прокси на том же сервере, можно заменить публикацию порта в Compose на `127.0.0.1:3010:3001`.

`POSTGRES_PASSWORD` и `INVITE_CODE` сохраните сгенерированными. `DATABASE_URL` из `.env` используется локальной разработкой; Compose сам задаёт внутренний адрес `db:5432`.

Для краткой проверки по `http://IP-СЕРВЕРА:3010` временно задайте именно этот `APP_ORIGIN` и `COOKIE_SECURE=false`. По обычному HTTP PWA не устанавливается, соединение не шифруется. Для друзей используйте HTTPS.

## 2. Собрать и запустить

```sh
docker compose up -d --build
docker compose ps
docker compose logs --tail=80 app
```

Приложение по умолчанию доступно на хосте: `http://127.0.0.1:3010`. Чтобы открыть порт внутри LAN, явно установите `APP_BIND=0.0.0.0`; для Cloudflare Tunnel это не нужно. Проверка готовности: `/api/health` должна вернуть `{"ok":true}`. Сборка рассчитана на x86-64 и ARM64; конкретную архитектуру вашего сервера нужно проверить на нём.

`compose.yml` содержит метаданные `x-casaos`. Установка через терминал надёжно сохраняет относительный контекст `build: .`. При импорте одного YAML в интерфейс CasaOS этот контекст может потеряться: сначала соберите образ `galinka-app:latest` в каталоге проекта, затем в импортируемой копии YAML замените `build: .` на `image: galinka-app:latest` и явно заполните переменные окружения в CasaOS. Не публикуйте такую копию с секретами в Git.

### Расшифровка голосовых

Docker-образ включает `whisper-cli` и многоязычную модель Whisper base Q5_1 (около 60 МБ).
Нажатие «Расшифровать» ставит запись в очередь. Сервер обрабатывает по одной записи на CPU
и сохраняет текст в PostgreSQL. Текст доступен участникам, которые видят это голосовое в чате.
После сборки образа распознавание работает автономно.

При запуске через Node установите ffmpeg и `whisper-cli`, скачайте модель и задайте
`WHISPER_MODEL` как абсолютный путь к ней. Если CLI отсутствует в PATH, задайте
`WHISPER_PATH` как путь к исполняемому файлу.
SHA-256 модели — `422f1ae452ade6f30a004d7e5c6a43195e4433bc370bf23fac9cc591f01a8898`.
[whisper.cpp](https://github.com/ggml-org/whisper.cpp) · [Скачать модель](https://huggingface.co/ggerganov/whisper.cpp/resolve/5359861c739e955e79d9a303bcbc70fb988958b1/ggml-base-q5_1.bin).

## 3. Включить HTTPS

На DNS направьте свой домен на сервер или существующий туннель. Настройте Caddy / Nginx Proxy Manager / свой reverse proxy на порт 3010. Пример Caddy, установленного на том же хосте:

```caddy
chat.example.com {
    reverse_proxy 127.0.0.1:3010 {
        flush_interval -1
    }
}
```

Пример фрагмента Nginx для уже настроенного TLS virtual host:

```nginx
location / {
    proxy_pass http://127.0.0.1:3010;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Forwarded-For $remote_addr;
    proxy_buffering off;
    proxy_read_timeout 90s;
    client_max_body_size 21m;
}
```

В контейнерном прокси `127.0.0.1` указывает на сам контейнер: используйте доступный ему адрес хоста или общую Docker-сеть. Для SSE важно отключить буферизацию и сохранить таймаут больше 25 секунд. При изменении `.env` пересоздайте приложение:

```sh
docker compose up -d --force-recreate app
```

## 4. Позвать друзей и установить приложение

1. Откройте HTTPS-домен и создайте аккаунт, используя `INVITE_CODE` из `.env`. Выдайте себе права: `docker compose exec app node scripts/grant-admin.mjs ЛОГИН`.
2. Приглашайте людей одноразовыми ссылками: «Администрирование» → «Приглашения». Каждая ссылка регистрирует одного человека и истекает через выбранный срок. После этого `INVITE_CODE` можно очистить в `.env` и пересоздать app: общий код перестанет работать, существующие аккаунты останутся.
3. «Новый чат» → найдите человека по имени или логину. В группе откройте «О чате» → «Ссылка-приглашение», чтобы добавить уже зарегистрированных.
4. Нелю включает владелец чата в «О чате». Команды: `@неля помощь`, `@неля монетка`, `@неля выбери пицца | суши`.
5. «Настройки» → «Установить Galinka». iOS: Safari → «Поделиться» → «На экран Домой». Android/ПК: Chrome/Edge → «Установить».

Установщики Windows/Linux/macOS, Android APK и пакет Arch Linux публикуются в GitHub Releases. На iOS доступна PWA. Android Push подключается через Firebase по инструкции [ANDROID.md](ANDROID.md); Web Push для браузеров и iOS PWA — по [WEB-PUSH.md](WEB-PUSH.md). Без соответствующей конфигурации этот канал уведомлений отключён. Сообщения сохраняются на сервере, при открытии клиент синхронизируется. При потере связи отправка показывает ошибку; текст остаётся в текущем окне для повторной отправки. Текстовые черновики сохраняются на устройстве между перезагрузками; вложения нужно прикреплять заново.

## 5. Резервное копирование

Сервис `backup` в `compose.yml` раз в сутки и сразу при запуске сохраняет базу и файлы в `./backups/<дата>/`. В каталоге лежат `galinka.dump` (`pg_dump -Fc`) и `uploads.tar.gz`. Во время копирования приложение продолжает работать.

Для проверки скрипт восстанавливает дамп во временную базу `galinka_restore_check`, считает сообщения и сверяет пути всех вложений с содержимым архива, включая перекодированные видео. Если между дампом и упаковкой вложение успело измениться или исчезнуть, скрипт повторяет копирование один раз. В `backups/` попадают проверенные копии. Срок хранения задаёт `BACKUP_KEEP_DAYS` (по умолчанию 14 дней), каталог — `BACKUP_DIR`.

```sh
docker compose up -d backup
docker compose logs backup        # «backup … ok: N messages, размер» или «backup FAILED»
```

Если приложение запущено из карточки CasaOS, добавьте сервис `backup` и в её `docker-compose.yml`. Храните копии ещё и вне сервера, отдельно сохраните `.env`.

Восстановление на чистый экземпляр (тома `galinka_postgres` и `galinka_uploads` пустые):

```sh
docker compose up -d db
docker compose exec -T db pg_restore -U galinka -d galinka --no-owner --clean --if-exists < backups/ДАТА/galinka.dump
docker run --rm -v galinka_uploads:/data -v "$PWD/backups/ДАТА:/backup:ro" alpine:3.22 tar xzf /backup/uploads.tar.gz -C /data
docker compose up -d
```

## 6. Обновления и обслуживание

Автоматический выкат с резервной копией БД, проверкой `/api/health` и `/api/version` и автоматическим откатом при неудачной проверке:

```sh
npm run deploy
```

Или напрямую:

```sh
sh scripts/deploy.sh
```

Скрипт перед `git pull --ff-only` сохраняет дамп PostgreSQL в `BACKUP_DIR` (`./backups`), собирает и перезапускает контейнеры с `BUILD_SHA=<commit>`, затем ждёт ответа `/api/health` (`{"ok":true}`) и совпадения `build` на `/api/version`. Если сборка или проверка здоровья не прошли, скрипт откатывает git-коммит, восстанавливает дамп базы и заново поднимает предыдущую версию.

Ручное обновление (без автоотката):

```sh
git pull --ff-only
docker compose up -d --build
```

Перед обновлением делайте резервную копию. Не меняйте major PostgreSQL с существующим томом без миграции. Не используйте `docker compose down -v`: ключ `-v` удалит постоянные данные.

Участники чата могут смотреть и слушать поддерживаемые медиа прямо в переписке. Остальные файлы выдаются как вложения для скачивания. Антивирусная проверка пока в плане. Сервер очищает незавершённые загрузки и отправленные без сообщения файлы через сутки. Пересланное вложение хранится, пока на него ссылается сообщение. Автоудаление сообщений задаётся отдельно для каждого чата.

## 7. Границы MVP и рост

- До 100 участников группы; до 50 при первоначальном создании, остальных добавляют приглашениями.
- До 10 вложений за отправку и 100 МБ на файл. Клиент передаёт файлы больше 4 МБ частями по 2 МБ. Квота пользователя — 500 МБ.
- Текст до 8000 символов. История и поиск — по 60 сообщений с курсором `(created_at, id)`.
- Cookie HttpOnly/SameSite=Strict; Secure для HTTPS. Пароли — scrypt с солью, в базе только хеши сессионных токенов. Защита от чужого Origin, SQL-параметры, проверки членства и rate limits.
- Лимиты запросов действуют на экземпляр API и IP. Пользователи за одним NAT делят лимит; для большой аудитории нужен общий шлюз/limiter.
- Нет E2EE, аккаунт-администрирования в интерфейсе, публичной регистрации, блокировок пользователей, модерации и восстановления паролей. Неля — явные команды, не нейросеть.
- Несколько API используют общую PostgreSQL и LISTEN/NOTIFY. До добавления реплик перенесите файлы на общий том/S3, настройте общий limiter, балансировщик и мониторинг. Используйте прямое подключение для LISTEN, а не PgBouncer в transaction pooling.
- Изменения схемы БД оформляются нумерованными SQL-миграциями в `server/migrations/` (таблица `schema_migrations`, выполнение под advisory lock при старте). Новые миграции сначала проверяйте на копии базы.

Для глобального запуска нужны нагрузочное тестирование, защита от злоупотреблений, жизненный цикл аккаунтов и аудит безопасности. Текущая версия предназначена для небольшой компании друзей.
