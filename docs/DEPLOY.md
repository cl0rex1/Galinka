# Рабочая схема Quiby

- `https://mess.quiby.me/` — сайт загрузки.
- `https://mess.quiby.me/app` — веб-клиент и адрес настольного приложения.
- `https://api.quiby.me/messenger/*` — REST API, файлы, SSE, версия и список сборок.

Cloudflare Tunnel `quiby-core` уже связан с Docker-сетью `quiby-core_default`. Добавьте только сервис Galinka к этой сети через `compose.edge.yml`. Маршруты, в таком порядке:

| Hostname      | Path                 | Service                              |
| ------------- | -------------------- | ------------------------------------ |
| api.quiby.me  | `^/messenger(/.*)?$` | `http://galinka:3001`                |
| mess.quiby.me | любой                | `http://galinka:3001`                |
| api.quiby.me  | любой                | прежний `http://quiby-core-api:3001` |

Не заменяйте существующий маршрут API Quiby и не публикуйте CasaOS или PostgreSQL. Поле Service URL не включает путь: приложение само преобразует `/messenger` во внутренний `/api`.

В `.env` на сервере:

```dotenv
APP_ORIGIN=https://mess.quiby.me
PUBLIC_API_ORIGIN=https://api.quiby.me
VITE_API_BASE=https://api.quiby.me/messenger
COOKIE_SECURE=true
TRUST_PROXY=1
EDGE_NETWORK=quiby-core_default
BUILD_SHA=0.2.0
```

Запуск: `docker compose -f compose.yml -f compose.edge.yml up -d --build`. Для каждого деплоя задавайте `BUILD_SHA` актуальным коммитом или версией; это же значение попадает в клиент, service worker и API версии. Локальный доступ к cookie по HTTP при `COOKIE_SECURE=true` не работает — используйте публичные HTTPS-домены.

В настройках приложения «Проверить обновления» сравнивает версию интерфейса с сервером. Настольная оболочка проверяет GitHub Releases и скачивает обновление только по нажатию пользователя. macOS auto-update требует подписанной сборки.

# Galinka на CasaOS

## 1. Подготовить каталог и секреты

На машине CasaOS в терминале (локально или через SSH):

```sh
mkdir -p /DATA/AppData
cd /DATA/AppData
git clone https://github.com/cl0rex1/Galinka.git
cd Galinka
docker run --rm --user "$(id -u):$(id -g)" -v "$PWD:/workspace" -w /workspace node:24-alpine node scripts/setup.mjs
```

Скрипт создаёт `.env` с правами `0600`, случайными паролем PostgreSQL и кодом регистрации. Повторный запуск не меняет существующий файл. Он не печатает секреты в консоль. Если `git` отсутствует, распакуйте архив исходников в этот каталог.

Откройте `.env` редактором и задайте:

```dotenv
APP_ORIGIN=https://chat.example.com
COOKIE_SECURE=true
TRUST_PROXY=1
```

`APP_ORIGIN` — ваш настоящий домен **без завершающего слеша и пути**. `TRUST_PROXY=1` подходит, если перед Node.js ровно один reverse proxy. Закройте прямой внешний доступ к порту 3010, оставив его доступным прокси. Если прокси на том же сервере, можно заменить публикацию порта в Compose на `127.0.0.1:3010:3001`.

`POSTGRES_PASSWORD` и `INVITE_CODE` сохраните сгенерированными. `DATABASE_URL` из `.env` используется локальной разработкой; Compose сам задаёт внутренний адрес `db:5432`.

Для краткой проверки по `http://IP-СЕРВЕРА:3010` временно задайте именно этот `APP_ORIGIN` и `COOKIE_SECURE=false`. По обычному HTTP PWA не устанавливается, соединение не шифруется. Для друзей используйте HTTPS.

## 2. Собрать и запустить

```sh
docker compose up -d --build
docker compose ps
docker compose logs --tail=80 app
```

Приложение по умолчанию доступно на хосте: `http://127.0.0.1:3010`. Чтобы открыть порт внутри LAN, явно установите `APP_BIND=0.0.0.0`; для Cloudflare Tunnel это не нужно. Проверка готовности: `/api/health` должна вернуть `{"ok":true}`. Сборка рассчитана на x86-64 и ARM64; конкретную архитектуру вашего сервера нужно проверить на нём.

`compose.yml` содержит метаданные `x-casaos`. Установка через терминал надёжно сохраняет относительный контекст `build: .`. При импорте одного YAML в интерфейс CasaOS этот контекст может потеряться: сначала соберите образ `galinka-app:latest` в каталоге проекта, затем в импортируемой копии YAML замените `build: .` на `image: galinka-app:latest` и явно заполните переменные окружения в CasaOS. Не публикуйте такую копию с секретами в Git.

## 3. Включить HTTPS

На DNS направьте свой домен на сервер или существующий туннель. Настройте Caddy / Nginx Proxy Manager / свой reverse proxy на порт 3010. Пример Caddy, установленного на том же хосте:

```caddy
chat.example.com {
    reverse_proxy 127.0.0.1:3010 {
        flush_interval -1
    }
}
```

Пример фрагмента Nginx для уже настроенного TLS virtual host:

```nginx
location / {
    proxy_pass http://127.0.0.1:3010;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Forwarded-For $remote_addr;
    proxy_buffering off;
    proxy_read_timeout 90s;
    client_max_body_size 21m;
}
```

В контейнерном прокси `127.0.0.1` указывает на сам контейнер: используйте доступный ему адрес хоста или общую Docker-сеть. Для SSE важно отключить буферизацию и сохранить таймаут больше 25 секунд. При изменении `.env` пересоздайте приложение:

```sh
docker compose up -d --force-recreate app
```

## 4. Позвать друзей и установить приложение

1. Откройте HTTPS-домен и создайте аккаунт, используя `INVITE_CODE` из `.env`.
2. Передайте друзьям адрес и код регистрации. Общий код можно сменить в `.env` с пересозданием app; существующие аккаунты продолжат работать.
3. «Новый чат» → найдите зарегистрированного друга по имени или логину. Либо создайте группу и используйте «Пригласить друзей» в её информации.
4. Подключите Нелю переключателем в группе. Попробуйте `@неля помощь`, `@неля монетка`, `@неля выбери пицца | суши`.
5. В Galinka откройте «Установить приложение». iOS: Safari → «Поделиться» → «На экран Домой». Android/ПК: Chrome/Edge → «Установить». macOS Safari: «Файл» → «Добавить в Dock».

Для Windows/Linux/macOS установщики публикуются в GitHub Releases; сайт показывает доступные сборки. На iOS/Android используется PWA. Фоновых push пока нет. Сообщения сохраняются на сервере, при открытии клиент синхронизируется. При потере связи отправка показывает ошибку; текст остаётся в текущем окне для повторной отправки. Черновики не сохраняются после перезагрузки страницы.

## 5. Резервное копирование

Нужны **база и файлы**. Имена томов по умолчанию `galinka_postgres` и `galinka_uploads`.

Для согласованной копии остановите только приложение, оставив БД работающей; создайте дамп и архив файлов, затем запустите приложение. Храните копии вне сервера в защищённом месте. Пример из каталога проекта:

```sh
mkdir -p backups
chmod 700 backups
docker compose stop app
docker compose exec -T db pg_dump -U galinka -d galinka -Fc > backups/galinka.dump
docker run --rm -v galinka_uploads:/data:ro -v "$PWD/backups:/backup" alpine:3.22 tar czf /backup/uploads.tar.gz -C /data .
docker compose start app
```

Эти фиксированные имена файлов перезаписывают предыдущую копию: добавляйте дату перед повторным запуском. Отдельно сохраните `.env` в защищённом хранилище. Проверьте восстановление на отдельном тестовом экземпляре, до того как полагаться на резервные копии.

## 6. Обновления и обслуживание

```sh
git pull --ff-only
docker compose up -d --build
```

Перед обновлением делайте резервную копию. Не меняйте major PostgreSQL с существующим томом без миграции. Не используйте `docker compose down -v`: ключ `-v` удалит постоянные данные.

Файлы хранятся без выполнения и выдаются как скачиваемые вложения с `nosniff`. Антивирус и предпросмотр не реализованы. Удаление сообщения удаляет его текст и реакции; сами загруженные файлы остаются в хранилище и входят в квоту. Файлы незавершённых отправок также входят в квоту; очистка пока выполняется администратором после резервной копии. Не удаляйте файлы из тома произвольно, чтобы не повредить существующие сообщения. Истёкшие сессии удаляются автоматически, историю сообщений приложение самостоятельно не удаляет.

## 7. Границы MVP и рост

- До 100 участников группы; до 50 при первоначальном создании, остальных добавляют приглашениями.
- Один файл на сообщение, до 20 МБ; суммарно 500 МБ на пользователя.
- Текст до 8000 символов. История и поиск — по 60 сообщений с курсором `(created_at, id)`.
- Cookie HttpOnly/SameSite=Strict; Secure для HTTPS. Пароли — scrypt с солью, в базе только хеши сессионных токенов. Защита от чужого Origin, SQL-параметры, проверки членства и rate limits.
- Лимиты запросов действуют на экземпляр API и IP. Пользователи за одним NAT делят лимит; для большой аудитории нужен общий шлюз/limiter.
- Нет E2EE, аккаунт-администрирования в интерфейсе, публичной регистрации, блокировок пользователей, модерации и восстановления паролей. Неля — явные команды, не нейросеть.
- Несколько API используют общую PostgreSQL и LISTEN/NOTIFY. До добавления реплик перенесите файлы на общий том/S3, настройте общий limiter, балансировщик и мониторинг. Используйте прямое подключение для LISTEN, а не PgBouncer в transaction pooling.
- Скрипт схемы защищён advisory lock; для следующих версий с изменением структуры понадобятся последовательные версионированные миграции. Сначала проверяйте их на копии базы.

Для глобального запуска нужны нагрузочное тестирование, защита от злоупотреблений, жизненный цикл аккаунтов и аудит безопасности. Текущая версия предназначена для небольшой компании друзей.
